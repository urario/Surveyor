# WindowsレガシーGUIアプリ向け GUIテスタビリティ解析ツール 要求仕様書

本書は、長期保守されている Windows デスクトップアプリケーション（C++/MFC 中心）を対象に、GUI テスト自動化の前段として既存画面のテスト容易性を評価・可視化する解析ツールの要求を定める。要求は RQ-xxx の識別子で管理する。

---

## 1. 前提

対象は、長期保守されている Windows デスクトップアプリケーションである。主な特徴は以下とする。

* C++ / MFC を中心とした既存アプリケーション
* Win32 GUI、独自コントロール、独自描画 UI を含む
* 画面数・操作パターン・回帰確認項目が多い
* 手動回帰試験の工数が大きい
* 将来的に自動 UI テストの導入を検討している
* ただし、既存画面の自動化適性が十分に把握できていない

### 1.1 解析方式の前提

本ツールは、実行中のアプリケーションを外部プロセスから動的に検査することを前提とする。

* 静的解析（リソーススクリプト／ソースコードの解析）は前提としない。
* 解析対象画面は、利用者（または将来的な自動操作）によって表示状態にされている必要がある。すなわち「ある画面を解析するには、その画面に遷移していること」が前提となる。
* 初期版では、画面への遷移は利用者が手動で操作し、本ツールが現在の対象ウィンドウを検査・撮像する運用を基本とする。自動ナビゲーションは初期版の対象外とする。
* この前提により、RQ-020（状態制御性）はツール自身の運用前提でもある（解析対象状態を作れない画面は、解析そのものが困難になり得る）。

### 1.2 「画面」の定義

本書でいう「画面」は、評価・出力の単位であり、以下のいずれか（または複合）を指し得る。具体的な単位は対象アプリに合わせて定義する。

* トップレベルウィンドウ（メインフレーム等）
* モーダル／モードレスダイアログ
* MDI／SDI の子ウィンドウ・ビュー
* プロパティシート／プロパティページ（タブ）
* ドッキングペイン、ツールウィンドウ

複数状態を持つ画面（タブ切替・モード切替等）は、必要に応じて状態別に評価できることが望ましい。

### 1.3 取得データモデルの前提と MFC 実態

本書で用いる AutomationId / Name / ControlType / Pane / Custom 等の用語は、UI Automation（UIA）／MSAA を介して外部から取得できる UI 情報を前提とする。ただし C++/MFC/Win32 では、WPF/UWP と取得実態が異なる点に留意する。

* 標準 Win32/MFC コントロール（リソーステンプレート由来）は、HWND とコントロール ID（リソース ID）を持ち、UIA 経由では AutomationId がコントロール ID から自動導出されることが多い。ウィンドウテキストは Name として取得され得る。したがって「識別子が全く無い」とは限らない。
* 一方、オーナードロー／独自描画コントロールや非 HWND 描画要素は、UIA ノードとして現れない（外部から要素として認識できない）ことがある。これが本ツールが主眼とする「独自 UI／自動化困難」の中心である。
* よって「AutomationId 付与」は、WPF のような単純なプロパティ設定ではなく、意味のある一意なコントロール ID の整備、または独自コントロールへの UIA プロバイダ（IRawElementProviderSimple）／ IAccessible 実装といった相応の改修を伴う。これを改善コストとして織り込む。

### 1.4 非侵襲性（read-only）の前提

本ツールは解析対象アプリの状態を変更しない（操作・入力・遷移を発生させない）ことを前提とする。詳細は RQ-048 に定める。

### 1.5 用語

| 用語 | 本書での意味 |
| -- | -- |
| AutomationId | UIA における要素の識別子。Win32 では多くの場合コントロール ID から自動導出される。実行間で安定し一意であるほど自動化に有利。 |
| Name | UIA における表示名。多くはウィンドウテキスト等に由来し、表示言語に依存しやすい。 |
| ControlType | UIA における要素種別（Button／Edit／Pane／Custom 等）。 |
| Pane / Custom | 汎用領域（Pane）や独自要素（Custom）。子要素が見えない大きな Pane や Custom は独自 UI 候補になりやすい。 |
| 安定識別子 | 実行間・改修間で変わりにくく、画面内で一意に要素を特定できる識別情報（AutomationId／コントロール ID／安定した Name 等）の総称。 |
| 座標依存 | 安定識別子・取得可能テキストが無く、要素矩形（座標）に頼らないと操作・特定できない状態。 |

### 1.6 本ツール自身の実装基盤の前提（WinUI 3 / C#）

本ツール（解析ツール本体）は、WinUI 3 / C#（.NET, Windows App SDK）を実装基盤とする。詳細な要求は RQ-054 に定める。前提として重要な点は以下。

* 実装基盤と解析対象は独立である。本ツールが WinUI 3 製であることと、解析対象が C++/MFC/Win32 であることは無関係である。本ツールは UIA のクライアントとして動作し、UIA はプロバイダ（対象アプリ側）とクライアント（検査側）がフレームワーク非依存に連携する。したがって「WinUI 3 のツールでは MFC アプリを見られないのでは」という懸念は当たらない。
* UIA ツリー取得方式（UIA COM API の直接利用、または同等ライブラリの採用）は別途選定する。WinUI 3 という選択自体は UIA クライアント方式を一意に決めない。
* 本ツールは UIA プロバイダではなくクライアントである。評価対象はあくまで「対象アプリの UIA ツリー」である。
* WinUI 3 は既定で Per-Monitor DPI Aware v2 であり、矩形と撮像の対応（RQ-027）に有利。ただし任意ウィンドウの撮像 API、パッケージ形態（MSIX／非パッケージ）、Windows App SDK ランタイム依存などの判断が伴う（RQ-027・RQ-049・RQ-054）。

### 1.7 本取り組みの位置づけ（近代化戦略との関係）

本ツールは単独のテスト容易性評価で完結するものではなく、より広い近代化戦略の前段に位置づく。背景にある意図は以下。

* ツール自身を最新スタックで保守したい。本ツールを WinUI 3 / C# で実装し、長期保守しやすい技術基盤に置く。
* 将来の MFC→WinUI 移行の布石とする。対象アプリを将来 WinUI 系へ移行する構想があり、その前段として既存 UI の棚卸し（画面・要素・独自描画箇所の把握）が必要になる。本ツールの構造的な解析出力は、その棚卸しにも資する。

ただし、初期版のスコープはあくまでテスト容易性の評価であり、移行作業や移行支援成果物の生成は対象外とする（再利用性の扱いは RQ-055）。テスト容易性の向上（安定識別子の整備・独自 UI の外部可視化）と移行準備は重なる部分が大きいが、同一ではない。

## 2. 解決したい課題

### RQ-001: 手動回帰試験の工数増大を抑制したい

既存アプリケーションでは、画面操作を伴う回帰確認が多く、リリースや変更のたびに大きな手動試験工数が発生している。すべてを自動 UI テスト化することは現実的ではないため、自動化すべき領域と、そうでない領域を判断できる状態にしたい。

---

### RQ-002: 自動 UI テスト導入による保守負債を避けたい

自動 UI テストは、導入方法を誤ると以下のリスクを持つ。

* 画面変更のたびにテストが壊れる
* 座標指定テストが大量に増える
* 画像マッチングの調整工数が増える
* テスト修正が開発のブレーキになる
* 本来削減したい工数が、別の保守工数に置き換わる

そのため、事前に既存画面の自動化しやすさを把握したい。

---

### RQ-003: 画面ごとの自動化適性を定量的に判断したい

現状では、各画面について以下のような判断が属人的になりやすい。

* この画面は自動化しやすいのか
* この画面は自動化すると壊れやすいのか
* どの程度の改修をすれば自動化できるのか
* 座標指定や画像認識に頼らざるを得ないのか
* そもそも GUI テスト対象にすべきなのか

これらを、画面ごとの評価結果として確認できるようにしたい。

---

### RQ-004: 安定識別子の不足を可視化したい

既存画面では、自動化に使える安定識別子（AutomationId／コントロール ID／安定した Name）が不足している要素が多い可能性がある。安定識別子が不足している場合、UI 要素の安定した識別が難しくなり、自動 UI テストの保守性が低下する。

そのため、画面ごとに以下を確認できるようにしたい。

* 安定識別子がある要素／ない要素
* 識別子はあるが一意でない／実行間で安定しない要素
* 識別情報を優先的に整備すべき要素
* 識別子不足が自動化に与える影響

評価は「有無」だけでなく、一意性・安定性まで含めて行う。標準 Win32/MFC コントロールは AutomationId がコントロール ID から自動導出されることが多く、有無だけでは実態を見誤るためである。また MFC での識別子整備は単純なプロパティ付与ではなく、意味あるコントロール ID 整備や独自 UI へのプロバイダ実装を伴い得る（改善コストとして扱う）。

---

### RQ-005: 独自 UI による自動化困難箇所を把握したい

独自描画 UI や独自コントロールでは、外部から UI 要素を認識できない場合がある。このような画面では通常の UI 自動化が難しく、座標指定や画像認識に依存しやすい。

そのため、以下のような箇所を抽出したい。

* 外部から子要素が見えない大きな画面領域
* 操作可能な部品として認識できない領域
* 表示上は複数部品に見えるが、解析上は単一領域に見える箇所
* 自動 UI テストよりも、アプリ側のテスタビリティ改善が必要な箇所

この抽出はヒューリスティック判定であり、誤検出（偽陽性・偽陰性）を含む。「正当に空のコンテナ」と「独自描画キャンバス」は外形が似る一方、一部の独自コントロールは独自 UI プロバイダ／IAccessible 実装により子要素を公開している場合がある。検出結果は確定ではなく候補として扱い、スナップショット（RQ-027）と併せて人が確認できることを前提とする。

---

### RQ-006: 座標指定・画像マッチング依存のリスクを把握したい

座標指定や画像マッチングは、解像度・DPI・フォント・テーマ・表示タイミング・画面レイアウト変更・表示言語・描画差分の影響を受けやすい。そのため、座標指定や画像マッチングに頼る可能性が高い画面・要素を事前に把握したい。

座標依存・画像依存は独立した欠陥ではなく、識別性（RQ-017）・独自 UI リスク（RQ-022）の結果として生じる。観点として完全には直交しないため、スコア化時に同一根因を多重計上しないよう扱う。

---

### RQ-007: 自動化の前に改善すべき画面を特定したい

自動 UI テストを作る前に、以下のような改善が必要な画面を特定したい。

* 識別可能な ID が不足している画面
* 結果判定に使える情報が外部から取得できない画面
* 独自 UI が多すぎる画面
* 座標指定以外の操作手段がない画面
* テスト前提状態を安定して作れない画面

これにより、テスト作成より先に行うべき改善を明確にしたい。

---

### RQ-008: 自動化対象の優先順位を決めたい

回帰試験削減効果が高く、かつ自動化しやすい画面から着手したい。そのため、画面ごとに以下を判断できるようにしたい。

* すぐ自動化できる画面
* 少し改善すれば自動化できる画面
* 限定的に自動化すべき画面
* 先にテスタビリティ改善が必要な画面
* GUI テスト対象から外すべき画面

---

### RQ-009: 開発者・QA・リーダーが同じ材料で議論できるようにしたい

自動 UI テスト導入の議論では、以下のような認識差が発生しやすい。

* 開発者は「自動化できる」と考える
* QA は「保守が大変」と考える
* リーダーは「投資対効果が見えない」と考える
* マネジメントは「どれだけ工数削減できるか」を知りたい

そのため、画面ごとの解析結果を共通の判断材料として提示できるようにしたい。多職種が読む前提のため、UIA 等の専門用語は 1.5 用語に定義する。

---

### RQ-010: 将来的に GUI 構造の劣化を検出できるようにしたい

一度テスタビリティを改善しても、その後の開発で以下が発生する可能性がある。

* AutomationId／コントロール ID が削除・変更される
* Name が空になる
* 識別しやすかった要素が認識しづらくなる
* 独自 UI 領域が増える
* テスト可能だった画面がテストしにくくなる

将来的には、こうした劣化を検出できる状態にしたい。

劣化検知は「同じ画面・同じ要素」を版間で対応付けられることを前提とする。ただし本ツールが検出する欠陥そのものが「識別子が不安定」であるため、要素単位の対応付けは原理的に難しい場合がある。比較の同一性管理方針は RQ-053 に定める（初期は画面単位・集計指標単位の比較を基本とし、要素対応付けはベストエフォートとする）。

---

### RQ-011: 問題箇所を画面上の位置として直感的に把握したい

AutomationId がない要素、Name が空の要素、独自 UI 候補、座標依存候補などは、属性一覧だけでは利用者が実際の画面上のどこを指しているのか分かりにくい。特に以下のような要素は、テキスト情報だけでは判断しづらい。

* 名無しパネル／名無しボタン
* 大きな独自描画領域
* 子要素が見えない Pane
* ControlType が Custom の領域
* 表示上は複数部品に見えるが、解析上は単一要素として見える領域

そのため、画面または部分画面のスナップショット画像を取得し、利用者が問題箇所を視覚的に把握できるようにしたい。撮像に伴う機密データの取り扱いは RQ-052 に定める。

---

## 3. 目指す状態

### RQ-012: 画面ごとのテスタビリティを一覧できること

対象アプリケーションの主要画面について、GUI テスト自動化のしやすさを一覧できること。一覧には、少なくとも画面名・評価結果・主なリスク・推奨される扱い・改善が必要な観点を含める。

---

### RQ-013: 自動化可否ではなく、自動化戦略を判断できること

単純に「できる／できない」ではなく、以下のような分類ができること。

| 分類 | 意味 |
| -- | -- |
| 即自動化候補 | 現状のままでも比較的安定して自動化できる |
| 小改善後に自動化 | 一部の識別情報や観測手段を追加すれば自動化しやすい |
| 限定自動化 | スモークテストや主要導線に限定すれば自動化可能 |
| 改善優先 | テストを作る前に画面側のテスタビリティ改善が必要 |
| 対象外候補 | GUI テストではなく下位層テストやログ検証で扱うべき |

---

### RQ-014: 自動化しない判断にも使えること

本ツールは、自動化対象を増やすためだけのものではない。以下の判断にも使えること。

* この画面は GUI テスト化しない
* この機能は下位層の自動テストで担保する
* この画面はログ検証や API 検証に逃がす
* この画面は手動確認を残す
* この画面は先に設計改善が必要

---

### RQ-015: 改善投資の説明に使えること

識別情報の整備、状態取得手段の追加、独自 UI の改善などは、短期的には開発工数を必要とする。そのため、以下を説明できる材料が必要である。

* どの画面に改善が必要か
* どの要素が自動化の障害になっているか
* 改善によりどの種類のテストが安定するか
* 改善しない場合にどのようなテスト保守リスクが残るか

---

### RQ-016: 解析結果を画面イメージと結び付けて確認できること

解析結果は、属性表だけでなく、実際の画面イメージと結び付けて確認できること。利用者が以下を直感的に理解できる状態を目指す。

* 問題のある要素が画面上のどこにあるか
* 名無し要素がどの表示領域を指しているか
* 独自 UI 候補がどの部分に該当するか
* 座標依存候補がどの部品・領域に対応するか
* 報告資料に画像を貼り付けて説明できるか

---

## 4. 評価したい観点

以下の観点は概念整理のための区分であり、互いに完全には独立しない。特に「座標依存リスク」は「要素識別性」「独自 UI リスク」の結果として生じるため、スコア化（RQ-034）では同一根因の多重計上に注意する。

### RQ-017: 要素識別性を評価できること

UI 要素を安定して特定できるかを評価したい。評価対象の例は以下。

* 安定識別子（AutomationId／コントロール ID）の有無
* 識別子の一意性（画面内で一意に特定できるか）
* 識別子の安定性（実行間・改修間で変わりにくいか）
* Name の有無・重複
* ControlType の妥当性
* 画面変更に対して識別方法が壊れにくいか

評価の主軸は「有無」より一意性・安定性に置く。また Name は表示言語に依存しやすく、多言語対応アプリでは Name 依存の識別は本質的に脆い。識別は Name より安定識別子を優先する観点を含める。

---

### RQ-018: 操作可能性を評価できること

UI 要素を外部から安定して操作できるかを評価したい。評価対象の例は以下。

* ボタンを押せるか／入力欄に値を設定できるか
* 選択肢を選べるか／チェック状態を変更できるか／スクロールできるか
* キーボード操作で代替できるか
* マウス座標に依存しない操作が可能か

UIA の操作可否は InvokePattern／ValuePattern 等のコントロールパターン対応状況に依存する点を、評価実装時の参考とする。

---

### RQ-019: 結果判定可能性を評価できること

テスト実行後に、成功・失敗を外部から判断できるかを評価したい。評価対象の例は以下。

* 結果テキスト／状態表示／エラー表示を取得できるか
* 一覧や表の内容を確認できるか
* ログや出力ファイルと紐づけて判定できるか
* 目視に近い画像判定へ過度に依存しないか

---

### RQ-020: 状態制御性を評価できること

テスト開始前の状態を安定して作れるかを評価したい。評価対象の例は以下。

* 初期画面を安定して表示できるか
* 前回実行状態の影響を排除できるか
* テストデータを用意できるか
* 外部装置や外部サーバ依存を制御できるか
* 画面遷移前提を自動で作れるか
* 非同期処理の完了を判定できるか

前提 1.1 のとおり、状態制御性は本ツールの解析運用自体にも影響する。

---

### RQ-021: 画面安定性を評価できること

画面表示やレイアウトがテスト保守性に与えるリスクを評価したい。評価対象の例は以下。

* 解像度差分／DPI 差分／フォント差分／表示タイミング差分に強いか
* レイアウト変更が頻繁に起きないか
* アニメーションやちらつきが少ないか

---

### RQ-022: 独自 UI リスクを評価できること

独自描画や独自コントロールにより、自動 UI テストが困難になるリスクを評価したい。評価対象の例は以下。

* 外部から部品単位で見えるか／子要素が取得できるか
* 操作対象として認識できるか／表示内容を取得できるか
* 結果判定に使える情報が取れるか
* 座標や画像に依存せずに扱えるか

RQ-005 と同様、本評価は候補抽出であり誤検出を含む。確定判断はスナップショット併用で人が行う前提とする。

---

### RQ-023: 座標依存リスクを評価できること

座標指定に頼らないと操作できない可能性を評価したい。評価対象の例は以下。

* 安定した要素識別子がない
* 表示テキストも取得できない
* 操作可能な部品として認識できない
* 要素矩形しか手掛かりがない
* 画像認識に頼らないと場所を特定できない

座標依存候補と画像マッチング候補は根因が重なる。区別する場合の目安は、「矩形は取れるが識別子が無い」を座標依存候補、「矩形・テキストとも信頼できず独自描画で位置特定が必要」を画像マッチング候補とする。

---

### RQ-024: 視覚的な説明可能性を評価できること

解析結果が、利用者にとって理解しやすい形で提示できるかを評価したい。評価対象の例は以下。

* 問題要素の位置を画面上で確認できるか
* 部分画面単位で確認できるか
* 属性一覧とスナップショット画像を対応付けられるか
* レビューや報告資料に使いやすいか
* 名無し要素や独自 UI 候補の実体を利用者が誤解なく把握できるか

---

## 5. 必要な出力

### RQ-025: 画面別評価一覧を出力できること

各画面について、画面名・評価結果・自動化戦略分類・主なリスク・優先的に改善すべき点を確認できること。

---

### RQ-026: UI 要素別の問題一覧を出力できること

各画面の UI 要素について、以下を確認できること。

* 識別情報が不足している要素
* 識別情報が一意でない／安定しない要素
* 表示名が空の要素／表示名が重複している要素
* 操作可能性が低い要素／結果判定に使いにくい要素
* 独自 UI 候補／座標依存候補

---

### RQ-027: 画面および部分画面のスナップショット画像を出力できること

解析対象の画面について、画面全体または問題箇所周辺のスナップショット画像を取得できること。スナップショット画像は、以下の用途に使えること。

* HTML レポート上で問題箇所を確認する
* 名無し要素が画面上のどこを指しているか確認する
* 独自 UI 候補の実体を確認する
* 座標依存候補の位置を確認する
* 報告資料やレビュー資料に画像として転用する
* 改善前後の説明材料にする

技術的事項として、撮像と要素矩形の対応を正しく取るため、本ツールは DPI アウェアであること、またスクロール外（オフスクリーン）要素・他ウィンドウによる遮蔽（オクルージョン）・マルチモニタの扱いを定義すること。撮像できない要素（非表示・スクロール外）は、その旨を結果に明示する。機密データの扱いは RQ-052 による。

WinUI 3 は既定で Per-Monitor DPI Aware v2 のため、UIA の BoundingRectangle（物理ピクセル）との対応付けに有利である。一方、WinUI 3 には任意ウィンドウの簡易スクリーンショット API が無いため、撮像方式は別途選定する（例：Win32 `PrintWindow`（`PW_RENDERFULLCONTENT` 併用）／ Windows.Graphics.Capture API 等）。`PrintWindow` は遮蔽に強いが一部の独自描画で欠落し得る、Graphics Capture は DWM 合成結果に忠実だが取得制約がある、といった得失を踏まえて決める。

---

### RQ-028: 問題要素とスナップショット画像を対応付けられること

問題として検出された UI 要素について、属性情報だけでなく、画面上の位置と対応付けて確認できること。対象例は以下。

* AutomationId がない要素／Name が空・重複の要素
* Custom UI 候補／大きな名無し Pane
* 座標依存候補／画像マッチング候補／結果判定に使いにくい領域

利用者が、一覧上の問題項目を見たときに、実際の画面のどこを指しているか把握できること。

---

### RQ-029: 改善候補を出力できること

自動化の保守性を高めるために、画面または要素ごとの改善候補を提示できること。改善候補の例は以下。

* 安定識別子（コントロール ID／AutomationId）を整備すべき
* 表示名を一意にすべき
* 結果判定に使える情報を取得可能にすべき
* 独自 UI の内部要素を外部から認識可能にすべき（プロバイダ／IAccessible 実装等）
* 座標依存のテスト対象から外すべき
* GUI テストではなく下位層テストで担保すべき

改善候補には、1.3 のとおり MFC では改修コストが伴うものがある旨を併記できることが望ましい。

---

### RQ-030: 人が読みやすいレポートを出力できること

解析結果は、開発者・QA・リーダーが確認できる形で出力すること。最低限、以下を満たすこと。

* 画面ごとの状況が分かる／高リスク画面が分かる
* 改善すべき UI 要素が分かる／自動化候補が分かる／自動化を避けるべき画面が分かる
* 問題箇所を画像で確認できる
* レビューや説明資料に転用できる

---

### RQ-031: 機械処理しやすい結果を出力できること

解析結果は、後続の集計・比較・CI 連携に使える形式でも出力できること。必要な用途は以下。

* 前回結果との比較／画面別スコアの集計／欠落情報の一覧化
* 改善状況の追跡／将来の CI 判定
* 別ツールや別 LLM によるレビュー
* スナップショット画像との対応関係の保持

比較用途を成立させるため、出力は決定性・再現性（同一入力・同一条件で同一結果）を満たすこと（RQ-051）。また、画面・要素・スナップショットを版間で対応付けるためのキーを含めること（RQ-053）。

---

## 6. MVP 範囲

### RQ-032: 初期版では主要画面の解析に集中すること

初期版では、全画面完全対応を目指さない。まずは、代表的な主要画面を対象に以下が確認できればよい。

* UI 要素の一覧／識別情報の有無／操作可能性の概況
* 独自 UI 候補／座標依存候補
* 簡易的な画面評価／改善候補／問題箇所のスナップショット画像

---

### RQ-033: 初期版では自動テスト実行を主目的にしないこと

初期版では、実際の GUI テストを大量実行することを目的にしない。優先するのは以下である。

* 既存画面の状態を知る／自動化しやすさを評価する
* リスクの高い画面を把握する／改善すべき箇所を見つける
* 自動化方針を決める／問題箇所を画面画像として確認できるようにする

---

### RQ-034: 初期版ではスコアは厳密性より説明可能性を重視すること

初期版の評価結果は、完全な数理モデルである必要はない。重要なのは以下である。

* 評価理由が説明できる／現場感覚と大きく乖離しない
* 改善前後の比較に使える／関係者の議論材料になる
* 自動化方針の優先順位付けに使える／問題要素の位置を画像で説明できる

説明可能性を重視する一方で、比較・追跡（RQ-010／RQ-031）に耐えるよう、スコアは決定的かつ再現可能に算出すること。簡易でも、同一条件なら同一スコアになる計算規則とする。観点間の非直交性（4 章冒頭）も考慮し、同一根因を二重に減点しない設計とする。

---

### RQ-046: 初期版の対象画面選定基準を定めること

「主要画面」を恣意的に選ばないため、対象画面は以下の観点で選定する。

* 回帰試験コストが高い（手動工数が大きい）
* 変更・実行頻度が高い
* UI パターンの代表性がある（標準コントロール中心の画面／独自 UI 中心の画面の両方を含む）
* 自動化の判断が割れている（属人的判断が起きやすい）

選定結果と選定理由を記録し、関係者が妥当性を確認できること。

---

## 7. 対象外

### RQ-035: 初期版では GUI テストコード生成を対象外とする

自動 UI テストコードの生成は、初期版の対象外とする。テストコード生成は、画面のテスタビリティ評価が一定程度できるようになった後の検討事項とする。

---

### RQ-036: 初期版では CI ゲート運用を対象外とする

CI でビルド失敗や警告を出す運用は、初期版の対象外とする。ただし、将来的に CI 連携できるよう、結果の保存・比較に使いやすい出力は意識する。

---

### RQ-037: 初期版では画像認識による自動操作を対象外とする

画像認識を使った自動操作は、初期版の対象外とする。画像認識が必要になりそうな箇所を検出することは対象に含めるが、画像認識テストを本格実行することは扱わない。なお、画面や部分画面のスナップショット画像を取得し、レポートに含めることは対象に含める。

---

### RQ-038: 初期版では独自 UI の改修自体を対象外とする

本ツールは、独自 UI を自動的に修正するものではない。独自 UI の問題箇所を見つけ、改善判断に使える情報を出すことまでを対象とする。本ツールは対象アプリのソースコード改変や識別子の自動付与を行わず、あくまで外部からの検査と報告に限る（非侵襲性は RQ-048）。

---

### RQ-039: 初期版では全画面完全網羅を求めない

初期版では、すべての画面、すべてのダイアログ、すべての状態を完全に解析することは求めない。まずは、代表的な主要画面で有効性を確認する（選定基準は RQ-046）。

---

## 8. 成功基準

### RQ-040: 自動化しやすい画面と危険な画面を区別できること

主要画面について、少なくとも以下を区別できること。

* 自動化しやすい画面／少し改善すれば自動化できる画面
* 自動化すると保守負荷が高くなりそうな画面／GUI テスト対象から外した方がよい画面

---

### RQ-041: 安定識別子の不足を説明できること

主要画面について、安定識別子（AutomationId／コントロール ID／安定 Name）の不足がどの程度あるかを説明できること。また、どの要素に優先的に識別情報を整備すべきかを説明できること。「有無」だけでなく、一意性・安定性の観点を含めること（RQ-017）。

---

### RQ-042: 独自 UI の影響を説明できること

主要画面について、独自 UI が自動化に与える影響を説明できること。特に、以下を明示できること。

* 外部から見えない領域／操作対象として扱いにくい領域
* 結果判定に使いにくい領域／座標指定や画像認識に依存しそうな領域

---

### RQ-043: 問題箇所を画像で説明できること

主要画面について、検出された問題箇所をスナップショット画像で説明できること。特に、以下を確認できること。

* 名無し要素が画面上のどこにあるか／大きな名無しパネルがどの領域か
* 独自 UI 候補がどの部分か／座標依存候補がどの部品か
* レビューや報告資料に画像を利用できるか

---

### RQ-044: 関係者の合意形成に使えること

解析結果をもとに、開発者、QA、リーダーが以下を議論できること。

* どこから自動化を始めるか／どこは自動化しないか／どこを先に改善するか
* どの画面は手動確認を残すか／どの機能は下位層テストに逃がすか
* 問題箇所が実際の画面上のどこにあるか

---

### RQ-045: 次フェーズの設計判断につながること

本仕様に基づく初期検討の結果、次フェーズで以下を判断できる状態にする。

* どの解析方式が必要か／どの情報を取得すべきか／どのレポートが有効か
* どのスコアリング観点が実用的か／どの範囲を MVP として実装すべきか
* 画面スナップショットをどの粒度で扱うべきか

---

### RQ-047: 評価結果が専門家判断と整合することを確認できること

初期版の評価が「現場感覚と乖離しない」ことを、検証可能な形で確認できること。

* 主要画面のうち一定数について、経験ある QA／開発者が手動で行った自動化適性判断と、本ツールの分類（RQ-013）を突き合わせる。
* 大きく食い違う画面については、原因（観点の重み付け・誤検出・前提差）を説明できる。
* この突き合わせ結果を、スコア規則の調整（キャリブレーション）に反映できる。

厳密な一致率目標は初期版では必須としないが、突き合わせ手続きと結果記録は行うこと。

---

## 9. 非機能要求・制約

### RQ-048: 非侵襲性（read-only）を満たすこと

本ツールは、解析対象アプリの状態を変更してはならない。

* 解析中に、ボタン押下・テキスト入力・選択変更・画面遷移などの操作を発生させない。
* 撮像・要素ツリー取得は読み取り専用で行う。
* 対象が業務データを保持している状態でも、データを破壊・送信・改変しない。

---

### RQ-049: 実行環境・権限の前提を明確にすること

本ツールの動作前提を明確にし、文書化すること。

* 対応 Windows バージョン、依存ランタイム（UIA／.NET 等）の前提
* 対象アプリと同一マシンでの実行可否、別プロセスからの検査可否
* 対象アプリが昇格（管理者権限）で動作する場合、本ツールも同等の整合性レベル／権限が必要になり得ること（権限不足時は検査できない要素が生じることを明示）

WinUI 3 実装に伴う前提として、以下も確定すること。

* 本ツールは Windows App SDK ランタイムに依存する。対象（開発・QA）端末への導入方法（ランタイム同梱／自己完結配置等）と対応 Windows バージョンを確定すること（具体バージョンは実装時に確定）。
* パッケージ形態（MSIX パッケージ／非パッケージ）を決めること。形態は配布・更新のしやすさと、UIA でのクロス整合性レベル検査の可否に影響する。
* 対象アプリより高い整合性レベルや、別整合性レベルのウィンドウを検査する必要がある場合、マニフェストの `uiAccess` 設定（署名・所定フォルダへの導入が前提）や昇格運用の要否を検討すること。社内ツールとして同一整合性レベルの対象のみを扱うなら不要な場合もある。

---

### RQ-050: 解析性能・規模の現実性を満たすこと

主要画面の解析が、実運用で許容できる時間・手間で完了すること。

* 1 画面あたりの解析・撮像時間の目安を把握できる
* 主要画面（数十画面規模を想定）の解析が現実的な工数で回せる
* 大量の子要素を持つ画面でも破綻しない（タイムアウト・件数上限等の扱いを定義）

---

### RQ-051: 結果の決定性・再現性を満たすこと

比較・追跡（RQ-010／RQ-031）の前提として、同一入力・同一条件での再実行時に、結果が安定して再現すること。

* スコア算出規則が決定的であること
* 取得順序や一時的な表示差で結果が大きくぶれないこと
* ぶれが避けられない要素（タイミング依存等）は、その旨を結果に明示すること

---

### RQ-052: スナップショット等の機密データを適切に取り扱うこと

スナップショット画像や取得テキストには、業務データ・個人情報・機微情報が含まれ得る。これらを安全に扱えること。

* 画像・テキストに機密情報が写り込む可能性を前提とする
* 必要に応じて、保存先の限定、共有範囲の管理、マスキング／ぼかし等の手段を選べる
* レポート（特に HTML）を配布する際の取り扱い注意を提示できる

---

### RQ-053: 画面・要素の同一性を管理できること

版間比較・劣化検知（RQ-010）と機械処理（RQ-031）のために、画面・要素・スナップショットを対応付ける識別キーを定義すること。

* 画面は安定したキー（ウィンドウクラス・タイトル・画面定義名等の組合せ）で識別する
* 要素対応付けは、識別子が不安定な要素が多いことを前提にベストエフォートとする
* 初期版の比較は、まず画面単位・集計指標単位で成立させ、要素単位の差分は補助的位置づけとする

---

### RQ-054: 本ツールの実装基盤を WinUI 3 / C# とすること

本ツール（解析ツール本体）は、WinUI 3 / C#（.NET, Windows App SDK）を実装基盤とする。この選択の意図は、ツール自身を最新スタックで保守し続けること、および将来的な MFC→WinUI 移行（近代化）の布石として移行の前段となる UI 棚卸し基盤を最新技術側に置くこと、にある（前提 1.7、RQ-055）。

* 本ツールは UIA のクライアントとして動作し、対象（C++/MFC/Win32）の UIA ツリーを検査する。実装基盤の選択は、検査対象のフレームワークを制約しない（前提 1.6）。
* 以下の実装上の判断点を、設計フェーズで確定すること（本仕様では方式を一意に固定しない）。
  * UIA クライアント方式：UIA COM API（IUIAutomation）の直接利用、または同等ライブラリ（例：FlaUI 等）の採用
  * 画面キャプチャ方式：Win32 `PrintWindow` ／ Windows.Graphics.Capture 等の選定（RQ-027）
  * パッケージ形態・権限：MSIX ／非パッケージ、`uiAccess`・昇格の要否（RQ-049）
  * レポート表示：HTML レポート（RQ-030）を本ツール内で表示する場合の手段（例：WebView2 の利用）
* 本仕様の他項目（非侵襲性 RQ-048、決定性 RQ-051、機密データ RQ-052 等）は実装基盤に関わらず満たすこと。
* 層分離：WinUI 3 は操作 UI ／レポート閲覧の基盤に限定し、解析ロジックは UI 非依存のライブラリとして分離する。最低限、次の層に分ける。
  * 解析コア（UIA クライアント、要素モデル、キャプチャ抽象化）：UI 非依存
  * 評価・スコアリング：純粋ロジック、UI・I/O 非依存（決定性は RQ-051）
  * 出力（HTML ／機械可読）生成：UI 非依存（RQ-030／RQ-031）
  * WinUI 3 アプリ：上記を呼び出す薄い UI シェル
  * （将来）CLI フロントエンド：同じ解析コア・評価・出力を再利用（RQ-031／RQ-036）
* この層分離により、本ツール自身の自動テスト（とりわけ評価ロジックの単体テスト）が容易になり、決定性（RQ-051）の担保にも資する。

---

### RQ-055: 解析結果が将来の近代化（MFC→WinUI 移行）計画に再利用できる余地を残すこと

本ツールは、より広い近代化戦略（将来的な MFC→WinUI 移行）の前段に位置づく（前提 1.7）。初期版のスコープは「テスト容易性の評価」であり、移行支援成果物の作成は対象外とするが、以下を満たすこと。

* 画面・UI 要素の構造棚卸し（画面一覧 RQ-025、要素一覧 RQ-026、独自 UI 候補 RQ-005／RQ-022）を、移行計画でも参照できる粒度・形式（機械可読 RQ-031）で保持する。
* 移行難易度に関わる観点（特に独自描画・非 HWND 領域、すなわち再実装が重い箇所）が、出力から読み取れることを妨げない。
* テスト容易性スコアは移行難易度スコアではない。観測・操作はできるが再実装は重い画面（またはその逆）があり得るため、両者を混同しないこと。

なお、移行手順の提示、移行先 WinUI コードや画面マッピングの生成、移行工数見積りは初期版の対象外とする。本要求は「将来の再利用を阻害しない」ことのみを求める。
